# Architecture

## Overview

A macOS host provisions x86 machines over the network and Raspberry Pis from SD cards. The host runs four services: dnsmasq (proxy DHCP + TFTP), nginx in Docker (HTTP), a root watcher that binds PXE clients to queued machine names, and an operator-owned REST + SSE API. Bash scripts behind `just` recipes create the queue, stage credentials and flash media. Python under `pxe-watcher/` owns all shared state.

### Boot chains

**x86 PXE.** UEFI PXE ROM → dnsmasq (proxy DHCP + TFTP) → GRUB → Ubuntu HWE kernel + initrd over TFTP → installer downloads the ISO over HTTP → autoinstall → late-commands fetch hostname and credentials by MAC → first boot with viam-agent, and Tailscale when the server has a key.

**x86 USB stick.** UEFI USB boot → GRUB on the stick → HWE kernel + initrd from the stick → installer downloads the ISO from the `IP:port` in the stick's `grub.cfg` → autoinstall → late-commands read `viam_hostname=` from `/proc/cmdline` and fetch credentials from `/machines/by-name/<name>/` → first boot. Only the HTTP server and API run.

**Raspberry Pi.** `flash-pi-sd.sh` writes the OS image, mounts the FAT32 boot partition and writes cloud-init `user-data`, `network-config` and `meta-data`. First boot configures the OS offline, then a systemd service does the network-dependent setup (packages, viam-agent, Tailscale).

## Data model

These paths are all under `http-server/machines/` unless noted. Every file the root watcher creates is chowned to the owner of that directory.

- **`queue.json`** is an array of entries. Only `queue_store.py` writes it, under an flock on `queue.lock` with temp-file-and-rename. An entry is `{"name", "assigned"}`. Full mode adds `slot_id` (`slot-<name>`), PXE assignment adds `mac`, and USB flashing adds `flashed_via`. A USB machine's failure markers and `done` warning are stored on its entry. Every lookup by name ignores case, since Viam treats such names as one machine (decision [41. Machine names follow Viam's rule, without a trailing hyphen](docs/decisions/0041-viam-machine-name-rule.md)).
- **`slot-<name>/viam.json`** contains the full-mode credentials, staged at provision time, before a MAC is known.
- **`<mac>/machine-info.json`** describes one PXE machine. Its fields are `name`, `mac`, `assigned_at`, `attempt`, `progress_at`, `completed_at`, `failed_at`/`failure_reason`/`failure_source` (`installer`, `timeout` or `reboot`), `armed`, and `warning` (from the `done` report; a new attempt clears it). Every change to an existing file goes through `watcher.update_info` (flock on `info.lock`).
- **`by-name/<name>/`** contains the credentials for USB machines, which fetch by name.
- **`netboot/grub/provisioned/<MAC>.cfg`** is the guard. Its presence makes GRUB exit to disk instead of installing.
- **`logs/events.jsonl`** is the event journal. Ids derive from the last line, read under the file's flock.
- **`logs/access.log`** is nginx's access log, mounted at `/var/log/pxe`, outside the served tree.
- **`~/Library/Application Support/Viam Provisioner/environments.json`** (app) contains the app's environments, sorted by name and written atomically. Each environment has `has…` flags for its secrets and never the secrets themselves. When an org's locations load, `EnvironmentsModel` stores each of its environments' location names. At launch it loads them for any `full` environment that has a location ID without a name, as an import leaves it. A key's granted locations fill only a missing name.
- **`~/Library/Application Support/Viam Provisioner/batches.json`** (app) lists the batches provisioned from this Mac, newest first, and is written atomically. Each batch records the environment, mode, org and location names, server, the names queued, and a sentence per machine that wasn't queued. Dates are numbers, seconds since 2001, and ISO 8601 strings from earlier files still read. An unreadable file is reported and never overwritten.
- **UserDefaults `server.name`, `server.url`** (app) store the chosen provisioning server.
- **Keychain service `com.bringingfire.viam-provisioner.environment-secrets`** (app) has one generic-password item per environment ID. Each item contains the OS password's SHA-512 crypt hash, the WiFi password and the Tailscale key.
- **Keychain service `com.bringingfire.viam-provisioner.api-keys`** (app) has one generic-password item per Viam API key. The account is the key ID, and the data is JSON with `keyID`, `key`, `scope` (`orgID`, `orgName`, and for a location key `locationID`, `locationName`) and `addedAt`. An item that can't be read or decoded is listed as unreadable, and the others load.
- **UserDefaults `ViamBaseURL`** (app) is the Viam app's URL, `https://app.viam.com` when unset.
- **Swift server data directory** (`--data-dir`) contains `queue.json` (entries in order, names as given), `machines/<name>.json` (attempt, stage, attempt start, progress, completion and failure, `steps` as `{step, at, attempt}` for every attempt, the boot files sent, the image download's bytes and total, and `secretsServed`: when each secret seed file was served this attempt), `credentials/<name>/viam.json`, `environment.json` and `token` (0600, directory 0700), and `events.jsonl`. Keys are lowercased names. Whole files are written to a temp file, fsynced, renamed into place, and the directory then synced. A failed directory sync is logged and keeps the write. The directory must lie outside `--files`, checked after resolving symlinks and `..`, since that tree is served to the network.
- **`/Library/Application Support/Viam Provisioner/Server/`** (server daemon) contains the server daemon's `data/` (its `--data-dir`) and `files/` (its `--files`), mode `0700`, owned by `_viamprovisioner`.
- **`config/site.env`** contains the site settings and is gitignored. `config/.server-address` contains the `IP:port` baked into USB sticks.

## Invariants

- **`queue.json` has one writer.** Scripts call the CLI of `queue_store.py`, and the watcher and API import it.
- **The queue is append-only.** `provision` adds machines after the highest existing `<prefix>-N` and skips names already queued. `just clean` is the only wipe.
- **The watcher keeps no state in memory.** It reads the queue and the MAC's `machine-info.json` on every PXE event, so `provision`, `reset`, `clean` and `unguard` take effect on a running daemon. A MAC that arrives with no slot is not remembered.
- **Guards are written on signs the installer is past its hostname fetch.** The watcher writes one on a 200 response to `GET /machines/<mac>/hostname` in the access log, and on a repeat PXE more than 60 seconds after assignment. The API writes one on a `done` report, and on progress past `identity` that clears a timeout failure.
- **The journal is the only IPC.** The root watcher and the operator-owned API both append to `logs/events.jsonl` under its flock, and the API tails it for SSE. A journal write failure is logged and never blocks assignment, guards or a recorded failure.
- **Entry status comes from disk.** `queued`/`flashed`/`assigned`/`installing`/`installed`/`failed` derive from `queue.json`, `machine-info.json` and the guard on every read. `failed` is checked first, because a failure removes the guard and a missing guard alone reads as `assigned`. `install-complete` is decided by `completed_at`, which is stamped before the event is emitted.
- **Crash recovery completes, never re-assigns.** The watcher completes an entry already assigned to a MAC instead of consuming a second slot.
- **A failure removes the guard, and the next PXE starts a new attempt.** A failed or `armed` MAC gets `attempt` + 1, a reset `assigned_at` and cleared markers, before the 60-second repeat-PXE rule is consulted. An installer failure replaces a timeout failure and then sticks. A timeout failure is cleared by later progress or a hostname fetch. A USB machine has no re-arm, so any progress after its failure clears it.
- **A repeat PXE with no sign of the installer is a failed boot.** Past the 60-second window, a machine with no progress report and no hostname-fetch guard records `install-failed` with source `reboot` and starts a new attempt. Machines assigned before attempts existed (no `attempt`) keep the old completion rule.
- **`done` completes a PXE install.** It stamps `completed_at` and emits `install-complete`, unless the machine is failed by the installer or armed by `just unguard`. A later PXE boot is the reboot that the guard sends to disk, and it changes nothing. A repeat PXE still completes a machine whose `done` never arrived. A USB machine is not completed: `InstallComplete` requires a `mac`. See decision [35. Complete an install on the installer's done report](docs/decisions/0035-complete-on-done.md).
- **Both templates install the same `viam-agent.service`.** `user-data.tpl` writes it from a heredoc and `pi-user-data.tpl` writes it with `printf`. Each has viam-agent's upstream settings: `User=root`, `Restart=always`, `StartLimitIntervalSec=0`, `TimeoutSec=240`, `KillMode=mixed`, `FinalKillSignal=SIGKILL`. viam-agent exits 0 when it restarts itself, so `Restart=on-failure` would leave it down. `test_installer.AgentUnitTest` asserts that the two are equal.
- **Installer reports contain no log text.** A reason is a fixed phrase plus at most the crash exception class, cleaned by the helper and again by the server.
- **The timeout is off unless passed.** The watcher's `--install-timeout-minutes` defaults to off, and `just serve` and the plist pass `INSTALL_TIMEOUT_MINUTES`.
- **Daemons run on a stable interpreter.** The interpreter is system or Homebrew `python3` ≥ 3.9, never the venv, and the code avoids 3.10-only syntax. The serving interface is baked into the plist at install. dnsmasq is stopped by pid file.
- **dnsmasq's proxy range follows the serving interface.** `pxe-subnet.sh` computes it at `just serve` or daemon install, and `PXE_PROXY_SUBNET` overrides it.
- **The Swift PXE server serves only inside its TFTP root.** `TFTPRoot` rejects paths that resolve outside it or to anything but a regular file, and the listener opens files non-blocking and checks the type again, so a FIFO can't stall the event loop. The interface MTU caps the block size, and `maxTransfers` caps concurrent transfers. A request beyond the cap gets a TFTP error.
- **A `PXEServer` starts once and stops once.** `start()` throws on a server that is starting, running or stopped, so no second set of sockets replaces the first. A failed bind closes the sockets already bound, and a `stop()` during `start()` returns only after that start has closed them. `events` keeps only the newest `eventBufferLimit` unread events, since every discover, firmware retries included, yields one.
- **The netboot daemon binds nothing until a peer asks.** It stores no interface or boot file, and `NetbootClient` asks again after a restart (decision [45. The helper serves on request and keeps no configuration](docs/decisions/0045-helper-serves-on-request.md)).
- **The netboot daemon writes only inside its TFTP root.** `TFTPRootFiles` refuses absolute paths, empty, `.` or `..` components, and paths whose directory resolves outside the root through a symlink. It removes only regular files.
- **The Swift DHCP sockets bind 0.0.0.0 pinned to the interface.** `InterfaceBinding` sets `IP_BOUND_IF` (`SO_BINDTODEVICE` on Linux), because on macOS a socket bound to a unicast address never receives broadcast discovers. See decision [28. Bind DHCP sockets to the interface, not its address](docs/decisions/0028-bind-dhcp-to-interface.md).
- **One process owns the Swift server's state.** The `Provisioner` actor reads and writes its data directory, and nothing else does, so it takes no file locks. A record is saved before its event is journaled, and a journal failure is logged and loses only the event. A newly queued name starts with no record and no staged files, and anything left under its key is cleared first. An unreadable machine record is logged and skipped, and an append after a torn journal line starts a new line.
- **A step advances only on an observation or a report.** A PXE observation bound to a queued name, an install report, or the image route's bytes record a step, and nothing infers one from another. Each attempt contains a step at most once, earlier attempts' steps stay, and `step-reached` is journaled only after the record is saved.
- **Swift server status derives from the machine record:** `failed`, then `installed`, then `installing` once any report arrived, then `assigned` when the current attempt has a step, else `queued`. `done` completes an install. Removal is refused only while `installing`.
- **The Swift server serves a machine's secrets once per attempt, at its seed path.** `user-data`, `viam.json` and `tailscale.key` are served from `/machines/by-name/<name>/<token>/` once each, and again only after a PXE offer to the bound machine (decision [51. A PXE boot of a bound machine re-arms its secrets](docs/decisions/0051-pxe-boot-re-arms-secrets.md)), never after an install report. Nothing is served after `done`. The served time is saved before the response, and a failed save serves nothing. `StaticFiles` never reads `/machines/` from disk and refuses `/config/` and `/autoinstall/`. See decision [52. Each machine fetches its config and secrets from a path carrying its token](docs/decisions/0052-seed-path.md).
- **Every environment value is checked before it is rendered.** Provisioning refuses control characters and line breaks in any field and checks username, timezone, packages and the robot network against fixed patterns, and the request's Host must be a host and port. `user-data.tpl` substitutes only `build-config.sh`'s list plus `MACHINE_URL`, and `RenderingTests` constrains the Swift renderer to that list.
- **Swift server 500s contain no Swift error text.** A failure the server names answers with a fixed sentence, and anything else answers `internal error`. The underlying error goes to the log.
- **Swift event streams end on graceful shutdown.** Hummingbird waits for in-flight responses, so each SSE body finishes itself when shutdown begins. A client that disconnects frees its stream slot at the next write, within one keepalive. A client that falls 256 events behind is dropped, and any end of a stream releases its slot.
- **The Python server ignores `environment` in provision requests.** `ProvisionRequest.environment` contains the settings that the Swift server renders into a machine's install config. The Python server accepts and drops it, and renders from `config/site.env`.
- **The handed-off key is created only after the operator confirms the code, and released only after the app commits to its public key.** Cancel, decline or timeout before creation leave no key in Viam. After creation, every failure path prints the key's name and where to delete it. See decision [40. Pair the app with an org API key minted by the viam CLI](docs/decisions/0040-pair-api-keys-from-the-viam-cli.md).
- **The app takes queue status from the server, never from events.** `QueueModel` replaces entries from `GET /queue` and, for each event not already in the snapshot, from `GET /queue/{name}`, and a 404 removes the entry. Queueing machines emits no event, so the app rereads the queue every 15 s and after each batch. Its reads run one at a time, so an older answer never replaces a newer one (decision [47. The Mac app's queue takes status from server reads](docs/decisions/0047-queue-status-from-server-reads.md)).
- **A machine created in Viam is either queued or reported.** `ProvisioningRun` lists each one the server didn't add, offers to resend those whose send failed, and deletes them from Viam on request.
- **The Mac app runs no `viam` command and reads nothing under `~/.viam/`.** Its keys are in the login keychain, and tokens are kept in memory only.
- **A key is stored only after Viam accepts it and its scope is worked out.** Errors, logs and `description`s never contain a key, and the Add Key form clears the key field on failure. A key Viam refuses later stays stored and is marked rejected.
- **A cancelled CLI call returns only after the child exits.** `ViamCLI.processRunner` terminates the child on cancellation and waits on its termination handler. `Process.terminationStatus` raises while the child runs.
- **`DeleteKey` returning NOT_FOUND counts as deleted** (decision [39. A NOT_FOUND from DeleteKey counts as deleted](docs/decisions/0039-not-found-counts-as-deleted.md)).
- **The app never stores an OS password, only its SHA-512 crypt hash.** Environment secrets are stored in the Keychain, and the JSON file contains only flags, which the store derives from the secrets it has. `just import-env` replaces an environment of the same name, keeping its ID and overwriting edits made in the app.
- **An action reads an environment only after the editor's unsaved edit is saved.** The editor saves a text field on Return or leaving it, so it registers its pending edit with `EnvironmentsModel`. `saved(id:)` and `duplicate(id:)` save the open editors' edits to that environment first. An action added beside Provision and Duplicate reads through `saved(id:)`.
- **Only the app creates and removes `_viamprovisioner` and the server directory,** each behind one administrator authorization. Enabling runs the create script only when the directory isn't the account's. Remove unregisters the server daemon before deleting either, so launchd can't start it against a half-removed account. Turning hosting off keeps both.
- **NIC names are discovered at install time.** The autoinstall config hardcodes no interface names.

## Boundaries

- **Targets know only the file server's `host:port`.** nginx forwards exactly `POST /api/v1/install-reports` (16 KiB body limit) to the API at `host.docker.internal`. The API's own port is open to any host on the network, targets included, and the split is two processes, not an access boundary.
- **The API runs as the operator, unauthenticated, on `0.0.0.0`.** It assumes a trusted lab network. It skips `getfqdn()` at bind so startup never waits on reverse DNS.
- **The org API key stays on the host.** Targets receive only their own `viam.json`.
- **The handoff listener binds loopback and caps request bodies at 64 KiB.**
- **The netboot daemon accepts XPC peers by code signature.** A team-signed netboot daemon requires the peer's team, and `provisioner-netbootctl` passes it, so every local user of a server Mac can drive the netboot daemon. An ad-hoc netboot daemon requires the identifiers `com.bringingfire.viam-provisioner.server` or `.netbootctl`, which any ad-hoc binary can claim, and a peer running as the user who owns the netboot daemon's executable.
- **The netboot daemon's TFTP root is root's alone.** Running as root, the daemon refuses to start on a root owned by another user or writable by group or others, and writes check the resolved directory before creating anything.
- **The image route serves only `--boot-image`.** `GET /pxe/{name}/{file}` answers for a queued name and the configured image's file name, counts the bytes sent, and journals `download-progress` at most every 5% and every 5 s. The OS name comes from the same flag, and the size comes from the file each request opens, so an image replaced in place is served whole. Reads go through NIO's file system, off the cooperative pool. Graceful shutdown ends a download, and its bytes are recorded as for a disconnect. A download records only against the queue entry it started for.
- **The Swift server's log contains nothing secret.** Every line is public in the unified log, so no line contains credentials, a seed file, the seed route's token or a query string; the request log replaces the token segment with `<token>`. Info lines are written at the unified log's Default level, because it keeps Info lines only in memory.
- **The server serves PXE itself, unprivileged, on one interface.** `--pxe-interface` or `<data-dir>/pxe.json` names it, every PXE socket binds `0.0.0.0` restricted to that interface, and TFTP serves only `<data-dir>/tftp`. A failed start leaves HTTP serving, reports `netboot` `down` and retries every 30 s (decision [50. Server mode is one unprivileged daemon that answers PXE itself](docs/decisions/0050-one-server-daemon.md)).
- **Under `just serve-usb` no watcher runs.** The API appends installer reports to the journal itself.

## API

`openapi/provisioner.yaml` is the contract. `pxe-watcher/test_contract.py` validates real responses and journal events against it. Every SSE frame's `data` contains `id`, `type` and `timestamp`. `GET /queue` returns `last_event_id` for snapshot-then-stream. A `resync` event means that the client's `Last-Event-ID` can't be served and that it should refetch `/queue`. The API advertises `_viam-provisioner._tcp` over Bonjour with `api=v1` in the TXT record.

## Boot order after install

The installer moves the disk above network boot with `efibootmgr`, from late-commands and again from a first-boot service, because efivars are not always writable in the installer chroot. Some firmware restores network-first anyway (issue [Minisforum UM890 BIOS ignores efibootmgr boot order (#4)](https://github.com/ashitaka1/viam-batch-provisioner/issues/4)). Every reboot then network-boots, and the guard sends it to disk. A machine whose firmware boots the disk first never PXEs again after install, so it stays `installing`.
