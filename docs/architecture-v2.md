# Provisioner v2 — Architecture Design

## Vision

Transform the batch provisioner from a local CLI workflow into a client-server system where:

- A **provisioning server** (macOS) runs permanently, owning PXE infrastructure and the install pipeline.
- **Native client apps** (macOS, iOS, iPadOS) let any team member provision machines without cloning repos, managing images, or running terminal commands.
- **One app, two roles.** The same macOS app is both the client and, when switched on, the server. Any Mac can become a provisioning server with a single toggle.
- The server holds no cloud credentials. Clients sign in to Viam as the user, create machines, then hand per-machine credential blobs to the server for staging.

## Principles

1. **The server is a provisioning engine, not a credential broker.** The user's Viam session never leaves the client. The server receives only per-machine identity + secret, scoped to one machine each.
2. **Camera-first hardware identification.** Scan a barcode or sticker on the chassis or a BIOS screen instead of copying MAC addresses. Physical-to-logical binding verified by a human, not inferred from boot order.
3. **Failure-forward notifications.** Success is expected; failures require action. Push failure alerts to the client (and phone) immediately.
4. **Contract-first, compiler-enforced.** The client-server protocol is defined once as an OpenAPI spec. Swift client and server code is generated from it, so contract drift is a build error. The spec is language-neutral, leaving the door open to non-Swift clients.
5. **Zero-dependency install.** Server and client both ship as a single app. No Homebrew packages, Docker, Python, or repo clone required to run either role.
6. **The existing tooling keeps working.** Bash scripts and Python watcher coexist in the repo until the Swift server replaces them. No big-bang migration.

## Components

### ProvisionerKit (shared Swift package)

Defines the protocol contract between server and client. Both sides depend on this library.

The wire types and client/server stubs are generated by `swift-openapi-generator` from `openapi/provisioner.yaml`. ProvisionerKit adds hand-written domain logic on top (queue state, event reduction, Bonjour discovery).

Types:
- `ProvisionRequest` — machine name, credential blob (viam.json contents), environment config
- `MachineEvent` — SSE event types: assigned, install-started, install-progress, install-complete, install-failed (with reason), guard-installed
- `QueueEntry` — name, MAC (optional until assigned), status enum, timestamps
- `EnvironmentConfig` — wifi SSID/password, SSH key, packages list, timezone, provision mode
- `ServerStatus` — service health (PXE responder, TFTP, HTTP), queue summary

### ProvisionerServer (Swift, Hummingbird or Vapor)

Replaces: dnsmasq, tcpdump-based Python watcher, nginx Docker container, provision-batch.sh queue logic, build-config.sh.

Responsibilities:
- **Native proxy DHCP responder** — answers PXE DHCP Discovers with boot server + filename (SwiftNIO, UDP 67/4011). Because it answers PXE requests itself, it sees every PXE client directly — no packet sniffing needed to learn MACs.
- **Native TFTP server** — serves GRUB, kernel, initrd, and per-MAC guard configs (SwiftNIO, UDP 69)
- **HTTP file server** — serves ISO, autoinstall configs, per-machine credentials
- **REST API** — accepts provision requests from clients, manages queue
- **SSE stream** — pushes machine events to connected clients in real time
- **Bonjour advertisement** — publishes `_viam-provisioner._tcp` so clients discover the server without typing an address
- **Autoinstall config generation** — renders user-data templates per machine
- **Queue management** — append-only queue supporting concurrent batches from different clients

Does NOT do:
- Create machines in Viam Cloud (client's job)
- Store or manage the user's Viam credentials

#### Privilege separation

DHCP and TFTP bind privileged ports. The server splits into:
- **ProvisionerHelper** — a small privileged launch daemon registered via `SMAppService` (macOS 13+). Owns the UDP sockets (proxy DHCP, TFTP) and nothing else. The user approves it once in System Settings.
- **The app process** — runs as the user. Hosts HTTP, REST/SSE, queue, and templating. Talks to the helper over XPC.

Keeping the privileged surface small limits what a bug in the HTTP/API layer can reach.

### ProvisionerApp (SwiftUI, macOS + iOS + iPadOS)

The operator-facing application. On macOS it also hosts the server role.

**Viam sign-in:**
- OAuth 2.0 authorization-code flow with PKCE via `ASWebAuthenticationSession` — the same login the first-party Viam mobile app uses
- Access and refresh tokens stored in Keychain; silent refresh
- Machines are created with the user's own permissions — whatever orgs and locations their account can reach
- API-key entry as a secondary path for service accounts

**Environment management:**
- Named environments ("teleop-demo," "lab-batch") with per-environment config
- Each stores: Viam org/location, name prefix, wifi, SSH key, packages, provision mode
- Org and location chosen from pickers populated by the signed-in account
- Environments persist locally; no server-side storage of client config

**Server discovery:**
- Bonjour browse for `_viam-provisioner._tcp` on the LAN
- Manual address entry as a fallback for networks that block mDNS

**Provisioning flow:**
1. Select environment, set count
2. App creates machines in Viam Cloud using the user's session
3. App fetches per-machine credentials (part ID + secret)
4. App POSTs each machine's name + credential blob to the server
5. Server stages credentials, adds machines to queue
6. SSE stream pushes events back: assigned, install started, complete, failed

**Camera integration (iOS, macOS with camera):**
- Scan barcode or label on physical hardware
- Read MAC addresses from a BIOS/firmware screen via Vision text recognition
- Associate serial number or asset tag with a machine name
- Optional: scan MAC address on chassis or screen to pre-bind a specific queue slot
- Asset inventory for free — serial ↔ machine name recorded in machine-info

**Notifications:**
- macOS: system notifications for install-complete and install-failed
- iOS: push notifications via APNs
- Failure notifications include failure reason, machine name, and install stage

**Status dashboard:**
- Live queue view — waiting, installing, complete, failed
- Per-machine detail: MAC, hostname, install stage, timestamps
- Historical batch view

#### Server mode (macOS only)

A "Host a provisioning server on this Mac" toggle turns the app into a server.

- **Menubar presence** (`MenuBarExtra`) — on/off switch, per-service health, live queue, log tail
- **First-run setup** — downloads the Ubuntu ISO, extracts GRUB/kernel/initrd, picks the serving network interface (replaces `just setup` and `pick-server-iface.sh`)
- **Launch at login** — the server comes back after a reboot
- A Mac in server mode is also a full client; the operator can provision from the same window

## Protocol

### Contract

`openapi/provisioner.yaml` is the source of truth. Swift client and server stubs are generated from it at build time. The Phase 2 Python server is validated against the same spec.

### Discovery

Server advertises `_viam-provisioner._tcp` over Bonjour with a TXT record carrying API version and server name. Clients browse and present discovered servers in a picker.

### REST Endpoints

```
POST   /api/v1/provision          Add machines to queue (body: [ProvisionRequest])
GET    /api/v1/queue              Current queue state
GET    /api/v1/queue/:name        Single machine status
DELETE /api/v1/queue/:name        Remove machine from queue (if unassigned)
GET    /api/v1/status             Server health + service status
GET    /api/v1/events             SSE stream (Accept: text/event-stream)
```

### SSE Events

```
event: machine-assigned
data: {"name": "lab-7", "mac": "aa:bb:cc:dd:ee:ff", "timestamp": "..."}

event: install-started
data: {"name": "lab-7", "mac": "aa:bb:cc:dd:ee:ff", "stage": "kernel-boot"}

event: install-complete
data: {"name": "lab-7", "mac": "aa:bb:cc:dd:ee:ff", "duration_seconds": 342}

event: install-failed
data: {"name": "lab-7", "mac": "aa:bb:cc:dd:ee:ff", "stage": "package-install", "reason": "network unreachable"}

event: guard-installed
data: {"name": "lab-7", "mac": "aa:bb:cc:dd:ee:ff"}
```

`Last-Event-ID` supported for reconnection — clients resume without missing events.

### Authentication

Two separate trust relationships:

- **Client → Viam Cloud:** OAuth as the signed-in user (see Viam sign-in above). Tokens stay on the client.
- **Client → provisioning server:** The server runs on a trusted lab network. Initial version: no auth on the API. If needed later: shared secret or mTLS. The server holds no sensitive data beyond per-machine credential blobs scoped to individual machines.

## Build Phases

### Phase 1 — Persistent server (current stack)

Make the existing Python/bash stack always-on. No Swift yet. Validates the "server runs forever, provision anytime" model.

- Watcher hot-reload: re-read queue.json on each PXE event instead of caching at startup
- Provision append: provision-batch.sh merges into existing queue instead of erroring
- launchd plists for dnsmasq, nginx (Docker), and watcher
- New justfile recipes: serve-daemon, stop-daemon, daemon-status

Starting points in the current code:
- `pxe-watcher/watcher.py` `watch()` loads the queue once (`queue = load_queue(queue_dir)`) and pops from that in-memory list in `assign_machine()`. Hot-reload means reading unassigned slots from `queue.json` at assignment time instead.
- `scripts/provision-batch.sh` "Check for existing batch state" block exits if any slot is unassigned, then deletes the old queue and slot dirs. Append mode replaces that with a merge; slot numbering in full mode must not collide with existing `slot-N` dirs.
- `just serve` wraps everything in a foreground trap that tears down on exit; the daemon recipes need their own lifecycle instead.
- PXE guards are written in two places: `watcher.py` `write_guard()` (repeat PXE after 60s) and `scripts/tail-http-logs.sh` (hostname fetched). A persistent setup needs whichever of these runs as a daemon — or both, deliberately.

### Phase 2 — Contract + REST API + SSE (Python)

Write the protocol spec, then implement it on the existing Python stack. Build and test the client against a real server before writing the Swift server.

- `openapi/provisioner.yaml` — endpoints, request/response schemas, SSE event schemas
- FastAPI server alongside the watcher, validated against the spec
- SSE event stream fed by watcher observations
- Bonjour advertisement (`dns-sd -R` under launchd)

### Phase 3 — Swift shared library + macOS app (client role)

Build ProvisionerKit and the macOS client against the Phase 2 Python server.

- ProvisionerKit: generated client + types, SSE consumer, Bonjour browser
- Viam OAuth sign-in (ASWebAuthenticationSession + PKCE, Keychain token storage)
- Viam Cloud integration: list orgs/locations, create machines, fetch credentials
- macOS app: environment management, provisioning flow, live queue, notifications
- Homebrew cask for distribution

### Phase 4 — Swift server + server mode

Replace the entire Python/bash/Docker server stack with the app's server mode.

- ProvisionerServer: HTTP file serving, REST/SSE from generated stubs, queue, templating
- ProvisionerPXE: native proxy DHCP + TFTP (replaces dnsmasq and tcpdump watcher)
- ProvisionerHelper: privileged daemon via SMAppService, XPC to the app
- Menubar UI: on/off, service health, queue, logs
- First-run setup: ISO download + GRUB/kernel extraction, interface selection
- Retire dnsmasq, Python watcher, nginx container, docker-compose.yml

### Phase 5 — iOS/iPadOS app + camera

Extend to mobile with platform-specific features.

- Shared SwiftUI views from macOS app
- Camera barcode/label scanning (AVFoundation) and BIOS-screen MAC reading (Vision)
- Push notifications via APNs
- Asset inventory: serial ↔ machine name binding

### Phase 6 — Polish

- Widgets (queue status on home screen / desktop)
- Shortcuts / Siri integration
- Historical batch analytics
- Multi-server support (connect to different provisioning servers)

## Open Questions

- **Install-failure detection.** Today the only completion signal is the installer fetching `/machines/<MAC>/hostname`; failures are silent. Options: autoinstall `error-commands` that POST a failure report to the server, stage-progress callbacks from `late-commands`, and a server-side timeout for machines that assigned but never reported. Failure notifications depend on this.
- **iOS notifications vs. a credential-free server.** iOS suspends background SSE connections, so mobile failure alerts need APNs. Sending APNs requires an Apple push key held by whatever sends the push — the LAN server or a relay. Decide where that key lives and whether it weakens the "server holds no meaningful credentials" principle.
- **Multi-client queue assignment.** With several clients queueing batches concurrently, which slot does an unrecognized PXE MAC get? Candidates: camera pre-binding required for concurrent batches, a per-server "active batch" selector, or FIFO across batches. Camera pre-binding also needs a defined fallback when an unbound MAC shows up.
- **Viam OAuth client registration.** Sign-in is supported (the first-party mobile app uses it); still need a client ID and redirect URI registered for this app, and confirmation of which API surface creates machines and fetches part credentials with a user token.
- **Pi SD card and USB stick modes.** v2 covers PXE. SD flashing and USB-stick creation need a home — client-side in the macOS app (it has disk access), or retired.
- **Apple distribution requirements.** Notarization, the SMAppService helper, and APNs all require a Developer ID / Apple Developer team. Decide whose account and signing identity ships the app.
- **Linux server.** Server mode is macOS-only (menubar, SMAppService). A headless Linux server would reuse ProvisionerServer and ProvisionerPXE under systemd, with status visible only from clients.
- **Hummingbird vs. Vapor.** Deferred to Phase 4; either works with swift-openapi-generator.

## Design Decisions

### Why the client creates machines, not the server

The user's Viam session (which can create and delete machines wherever the user has rights) stays on the client, protected by the OS Keychain. The server only receives per-machine credentials scoped to one machine each. If the server is compromised, the blast radius is the machines currently in the queue — not the user's account or org.

### Why OAuth instead of API keys

Users sign in the way they already do in the first-party Viam mobile app. No minting, copying, or rotating keys, and the app acts with exactly the user's permissions. API keys remain available for service accounts.

### Why camera over MAC-address inference

The watcher assigns names in boot order. If two machines PXE boot simultaneously, the name-to-physical-machine binding is arbitrary. Camera scanning creates a human-verified physical-to-logical binding. Serial numbers and asset tags provide a hardware inventory as a side effect.

### Why SSE over WebSocket

The client's actions (provision, query) are naturally request/response. The server's push channel (events) is one-directional. SSE fits this exactly — simpler than WebSocket, with built-in reconnection via Last-Event-ID. The REST half stays debuggable with curl.

### Why OpenAPI instead of distributed actors

Swift distributed actors would give compile-time-checked remote calls, but lock both ends to Swift. An OpenAPI spec with `swift-openapi-generator` gives the same compiler-enforced contract on the Swift side, while remaining implementable in Python (Phase 2) and consumable from Kotlin or other languages if Android or Linux clients are ever built.

### Why native PXE instead of dnsmasq

dnsmasq answers PXE requests while a separate tcpdump watcher sniffs the wire to learn which MACs showed up — two programs reconstructing one event. A native proxy DHCP responder sees each PXE client because it is the one answering, which removes the watcher, the sniffing, and the external dependency. Proxy DHCP and TFTP are small, well-specified protocols (RFC 4578 PXE options, RFC 1350 TFTP).

### Why one app for client and server

A single distributable covers both roles, so standing up a new provisioning server is "install the app, flip the toggle." Server mode reuses the client's views for queue and status, and the operator on the server Mac provisions from the same window.

### Why Swift on the server

Shared generated types with the client apps, and Swift's async/await and SwiftNIO fit the server's workload (UDP PXE + TFTP, HTTP serving, SSE broadcasting). The practical path: build the client against the Python server first (Phases 2–3), then swap to Swift (Phase 4) knowing the protocol is right.

### Why coexist in one repo

The Swift and Python/bash codebases share netboot configs, autoinstall templates, and GRUB assets. The existing tooling works for debugging and one-off operations even after the Swift server is live. Splitting repos would duplicate assets or add submodule complexity.
